# ProxyCore Security and Operations

Safe enough for a carefully exposed homelab ingress path, without pretending the host OS or network is risk-free. Goal: reduce blast radius, keep secrets out of ordinary paths, and make apply/rollback observable.

## Assumptions

- One trusted operator owns the host.
- Host OS, Docker, and physical network are outside ProxyCore's direct control.
- Upstreams may be private/loopback/Docker addresses by operator choice.
- Control plane may be Internet-reachable only through intentional TLS and auth.

## Assets and controls

| Asset | Control |
| --- | --- |
| Local passwords/sessions | Strong hashing, Secure/HttpOnly cookies, revocation, audit |
| Provider credentials / TLS keys | Encrypt at rest, master key outside Postgres, redaction |
| DNS/Nginx desired state | Typed validation, revisioning, validate-before-reload, rollback |
| Worker privileges | Separate from web; no raw Docker socket on web or worker; fixed helper operations only |
| Forwarded DNS | Visible forwarder health; managed zones never silently replaced by forward answers |

## Trust boundaries

1. Browser → control plane (untrusted input)
2. Control plane → PostgreSQL
3. Control plane → worker (job contract only)
4. Worker → service-control helper (private Unix socket; fixed operations)
5. Service-control helper → Nginx/CoreDNS (constrained validate/reload)
6. Nginx → upstreams
7. CoreDNS → configured forwarders
8. Control plane → Cloudflare DNS-01 (optional, scoped)

## Identity (MVP)

- Local username/password only
- One installation with Owner and Operator roles; server-side checks on every mutation
- Bootstrap creates the first Owner
- Owner manages user CRUD
- OIDC and MFA are deferred

## Secrets

- Master key outside PostgreSQL
- Encrypt credentials, Basic Auth password hashes, and certificate private keys at rest
- Never return plaintext secrets in API/log/audit/rendered non-secret config
- Basic Auth stores an encrypted `{SHA}` hash referenced by `passwordSecretId`; the worker writes htpasswd files into the Nginx candidate directory
- Fail closed if the key is unavailable

## Input safety

### DNS

Canonicalize names; type-validate values; enforce TTL bounds and CNAME rules; treat wildcards as DNS labels, not regexes; structure-render all CoreDNS output.

### Forwarding

Only explicit DNS IP:port endpoints; ordered fallback; managed zones authoritative first; forwarder failure is visible.

### Upstreams / Nginx

Literal IP/port/protocol only; typed policy fields plus explicitly bounded server-level Nginx directives from the Record dialog; exact/prefix path rules with deterministic precedence; `nginx -t` before reload; Basic Auth requires client TLS; HTTPS default on but disableable per proxied record; HTTP/2 and HTTP/3 are explicit proxied-record settings; HTTP/3 requires verified binary support plus TCP/UDP 443; proxied DNS answers must be ingress addresses (never origin) while proxy is on; trusted proxy CIDRs only when configured.

## TLS operations

| Mode | Use |
| --- | --- |
| Self-signed | Internal names / no public challenge |
| Let's Encrypt HTTP-01 | Publicly reachable hostnames |
| Let's Encrypt DNS-01 | Via Cloudflare `_acme-challenge` only |

Renewal failure keeps the current valid certificate and surfaces expiry risk. Backend HTTPS verification is explicit per proxied record and off by default for homelab origins; client-facing certs remain validated by ProxyCore policy.

## Logging and audit

- Operational logs for diagnosis
- Audit events for who changed what
- Correlation IDs; secret redaction
- In-app job/health/certificate status
- Configurable retention: 7 days or 50 MB by default, whichever limit is reached first
- No Prometheus or webhook alert system in MVP

## Primary–Node continuity threat model (Phase 0+)

The PRIMARY/NODE topology introduced by `docs/prd-primary-node-continuity.md`
extends the trust boundaries above with an additional network: the
authenticated channel between a primary and its enrolled nodes.

### Additional assets

| Asset | Control |
| --- | --- |
| Cluster KEK (32-byte AES-256) | Generated by primary, shared with nodes at enrollment, stored locally wrapped with the installation master key, never sent in cleartext after enrollment |
| Node credentials | Per-node revocable credential, replaces the enrollment token after Phase 2 enrollment completes |
| Enrollment tokens | Short-lived, single-use, opaque, hashed at rest, Owner-mint only, never returned in plain after the call |
| Snapshot envelope integrity | SHA-256 content hash over canonical ReplicatedFields; AES-256-GCM wrapping for any secret referenced by id |
| Snapshot delivery transport | Authenticated and encrypted on the LAN even when the LAN is private |
| Node-local ingress address | Operator-configured per node, never derived from the snapshot, never overwritten by an import |
| Stale-primary state | Logged at startup; the API boundary in Phase 2/3 will reject ordinary writes |
| Local Owner emergency credential | Generated at enrollment, replicated hashes plus a node-local credential usable without contacting the primary |

### Threat actors

1. **LAN attacker who can intercept unauthenticated traffic.** Mitigated
   by authenticated and encrypted transport for snapshot delivery and
   for the enrollment channel. Even on a private LAN, the primary/node
   API treats the channel as untrusted.
2. **Rogue former primary that returned after a newer leadership
   generation was promoted.** Mitigated by the leadership-generation
   comparison, the stale-primary startup guard, and the rule that a
   returning former primary MUST NOT automatically overwrite the new
   primary.
3. **Compromised node holding a valid node credential.** Mitigated by
   per-node revocation at the primary, by binding the credential to a
   specific installation id, and by limiting the node's authority to
   read snapshots and report acknowledgements.
4. **Insider with read access to the database.** Mitigated by wrapping
   the cluster KEK with the installation master key (which lives
   outside PostgreSQL) and by AES-256-GCM protection of every secret
   referenced by a snapshot. Plaintext secrets never appear in the
   database, in API responses, or in audit logs.
5. **Snapshot replay from an older leadership generation.** Mitigated by
   the leadership-generation field in the envelope and by the node's
   stale-primary guard: a snapshot whose generation is strictly older
   than the local latest-known generation is rejected.

### Enrollment threat model

- Enrollment begins with the primary minting a short-lived opaque token
  (configurable TTL, single use). The token is presented by the node
  over the existing authenticated API surface; it is never returned in
  plain after the API call, and the row stored server-side is the
  token's hash, not the token itself.
- The node MUST verify the primary identity (installation id and
  certificate fingerprint) BEFORE destructive replacement of its local
  configuration.
- The primary MUST display to the Owner the node identity that will be
  enrolled and the destructive consequences, and require explicit
  confirmation.
- After a successful exchange, the node receives a per-node revocable
  credential. The enrollment token is invalidated immediately; future
  requests use the credential.

### Snapshot delivery threat model

- Transport: authenticated and encrypted. Even when the LAN is private,
  the snapshot endpoint MUST refuse requests without valid credentials.
- Integrity: every snapshot carries a SHA-256 content hash over
  ReplicatedFields. The node verifies the hash before any side effect.
- Tampering: any modification of ReplicatedFields breaks the hash; the
  node rejects the snapshot and logs the rejection reason.
- Replay: snapshots include a leadership generation. A snapshot whose
  generation is older than the local latest-known generation is
  rejected.
- Substitution: a snapshot claiming a different source primary id than
  the one the node enrolled with is rejected.
- Node-local integrity: NodeLocalFields are authoritative on the
  receiving node; the importer replaces them with the locally
  configured values before apply, so a hostile primary cannot redirect
  the node's data plane ingress.

### Secret transport threat model

- The cluster KEK is a 32-byte AES-256 key generated on the primary
  during enrollment.
- It travels to the node exactly once, over the authenticated
  enrollment channel, wrapped in the enrollment transport.
- After enrollment, the KEK is stored on both sides encrypted with the
  local installation master key. The master key never leaves the host.
- Replicated secrets are wrapped in a `v1.kek:<iv>:<tag>:<ciphertext>`
  envelope with AES-256-GCM. The envelope is intentionally distinct
  from the local-master-key envelope so a reader can route to the
  right decryption path by prefix alone.
- Promotion does not require re-encryption: the new primary retains
  the cluster KEK and can decrypt every replicated secret.
- Rotation hooks (Phase 4) replace the cluster KEK by minting a new
  KEK, re-wrapping every replicated secret, and asking each node to
  switch over. The legacy KEK is retired but retained for one
  transition cycle so an in-flight snapshot can still be decrypted.

### Split-brain threat model

- The local installation tracks `latest_known_generation`. If an
  imported snapshot reports a generation strictly greater than the
  local `leadership_generation`, the node enters stale-primary guarded
  state, blocks ordinary writes, and surfaces the situation to the
  operator.
- A former primary that returns after a newer generation was promoted
  is NOT automatically demoted; it observes the newer generation, logs
  the warning, blocks configuration writes, and requires explicit
  recovery: rejoin as a node, or be re-promoted after the operator
  acknowledges split-brain risk.
- The primary UI shows every node's last seen, downloaded, and applied
  versions so an operator can spot drift before it becomes user-visible.

### Rejected alternatives

- Sharing secrets by transport-decrypt-and-re-encrypt with the
  node-local key: more complex and requires offline re-encryption on
  promotion; the cluster KEK model achieves the same outcome with one
  envelope format and no promotion-time re-encryption.
- Primary-push transport: requires an inbound management endpoint on
  the node beyond its existing UI/API; introduces additional attack
  surface on the LAN. Node-pull is preferred.
- Automatic failback: violates the explicit non-goal "failback is never
  automatic". The operator decides when a former primary rejoins.

## Backup

Post-MVP. Production-like migrations need preflight and Owner-acknowledged manual recovery until backup exists.

## Runbooks required before production-like use

- Bootstrap Owner and create operators
- Apply/roll back DNS change (managed + forwarder)
- Apply/roll back proxied A/AAAA/CNAME (DNS ingress answer + Nginx TLS on/off, HTTP/2, optional HTTP/3)
- Issue self-signed and staging LE certs (HTTP-01 and DNS-01)
- Recover from invalid Nginx or CoreDNS candidate
- Rotate master key / Cloudflare DNS-01 credential

## Security checklist

- [ ] Web cannot run arbitrary host commands or hold Docker socket
- [ ] Worker has no raw Docker socket
- [ ] Service-control helper socket is private to the worker
- [ ] Worker reload path is constrained
- [ ] Worker service-control operations are fixed and cannot execute user-supplied commands
- [ ] Mutations are server-authorized
- [ ] Secrets/keys encrypted and redacted
- [ ] Candidates validated before reload
- [ ] Unmanaged DNS forwarding works and fails visibly
- [ ] Basic Auth cannot enable on cleartext client routes
- [ ] HTTP/3 is enabled only after binary support and TCP/UDP 443 are verified
- [ ] CoreDNS not publicly exposed by default
- [ ] Trusted tunnel headers cannot be spoofed on the direct path
- [ ] PRIMARY/NODE enrollment uses a single-use short-lived token; the token hash is stored, not the token
- [ ] Snapshot delivery is authenticated and encrypted; content hash verified before any side effect
- [ ] Cluster KEK is generated on the primary, shared once at enrollment, and stored locally wrapped with the master key
- [ ] Stale-primary guard logs at startup and (in Phase 2/3) blocks ordinary writes at the API boundary
- [ ] Former primary cannot silently resume writable operation after a newer leadership generation was promoted elsewhere
- [ ] Node-local ingress address is operator-configured per node and never overwritten by an imported snapshot

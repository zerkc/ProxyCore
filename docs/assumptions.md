# ProxyCore Implementation Assumptions

This file records implementation choices that are not fully specified by the
MVP contracts. They are intentionally reversible. A correction should update
the affected code, tests, OpenSpec artifact, and (when the security or product
boundary changes) `docs/decision-log.md`.

| ID | Status | Choice | Reason | Impact | Verification / correction path |
| --- | --- | --- | --- | --- | --- |
| ASM-001 | accepted | Use Vitest with TypeScript scripts for unit and application tests. | The contracts require TDD but do not name a runner. | Adds a development-only test tool and standardizes `bun run test`. | Replace the runner in `package.json`, `openspec/config.yaml`, and CI scripts if preferred. |
| ASM-002 | accepted | Use a Bun workspace with `apps/` and `packages/` boundaries (DEC-051). | The MVP contains UI, worker, helper, renderers, and shared domain code. | Keeps privileged code out of the UI package and allows focused commits. | Typecheck package boundaries and remove a package only with its tests and imports. |
| ASM-003 | accepted | Use REST-style Next.js App Router route handlers for the control-plane API. | The documents define observable actions but no wire contract. | API paths and JSON payloads become the initial public application contract. | Contract tests cover each handler; a later RPC/API redesign must update the OpenSpec API section. |
| ASM-004 | accepted | Use Node.js `scrypt` with random salts for password hashing and opaque, hashed session tokens stored in PostgreSQL. | It provides a secure standard-library baseline without adding a native password dependency. | Password parameters and session expiry are configuration values. | Auth tests cover hash non-reversibility, login, expiry, and revocation. |
| ASM-005 | accepted | Keep domain/application tests runnable with in-memory ports; use PostgreSQL and Compose only for integration verification. | Docker is unavailable during the normal development phase. | In-memory adapters must preserve the same invariants as persistent adapters. | PostgreSQL migration and Compose tests are final-phase gates; persistence contract tests run against both ports. |
| ASM-006 | accepted | Run retention cleanup from the worker loop and expose an explicit cleanup operation; do not add a separate scheduler service. | The cleanup scheduler and storage placement were left open and a single worker is already required. | Cleanup is best-effort and observable through worker status/logs. | Test age/size limits and preservation of desired/applied state and active certificates. |
| ASM-007 | accepted | The control helper is the only component allowed to use a deployment control mechanism; worker requests a fixed allowlisted operation over a private Unix socket. | This resolves the worker/helper ambiguity in favor of the least-privileged boundary. | Compose may grant the helper the minimum control capability; web and worker receive no Docker socket. | Protocol tests reject unknown operations and user-supplied commands; Compose inspection verifies mounts. Promote to a decision if the boundary changes. |
| ASM-008 | accepted | Implement CoreDNS and Nginx renderers as pure deterministic functions, with service execution behind ports. | Rendering must be testable without services and secrets must not leak into candidates. | Candidate files and checksums are stable fixtures. | Golden/fixture tests and final `coredns`/`nginx -t` verification. |
| ASM-009 | accepted | Implement real ACME/Cloudflare adapters behind interfaces and fake deterministic adapters for TDD; no live credentials are stored in the repository. | The user confirmed both adapter types while no credentials/domains were supplied. | Live issuance is environment-dependent and may remain unverified. | Fake adapter tests run normally; live staging tests run only with supplied secrets in the final phase. |
| ASM-010 | accepted | Generate self-signed certificates with a pure TypeScript-compatible library and store private keys encrypted through the shared secret service. | Node's standard library does not provide a convenient X.509 certificate builder. | The certificate package is isolated behind a small certificate port. | Certificate parsing and TLS fixture tests; replace the library without changing the port. |
| ASM-011 | accepted | Treat the Next.js UI as a functional administration surface, not a pixel-identical design deliverable. | The docs define journeys and fields, not visual specifications. | All MVP actions are reachable with accessible forms/tables/status views. | Route/component tests and manual journey checks; visual redesign remains additive. |
| ASM-012 | accepted | Use environment variables for database URL, master key, session policy, ingress defaults, and external provider credentials. | Deployment secrets must remain outside source control. | Missing required secrets fail closed at startup or at the operation boundary. | Startup/config tests and Compose `.env.example`; never commit real values. |
| ASM-013 | accepted | HTTP-01 challenge serving is represented by the certificate/job boundary and a controlled challenge artifact; Nginx integration is validated in Compose. | The docs require issuance but do not define a separate challenge entity or route API. | The worker owns challenge lifecycle and cleanup. | Fake ACME tests cover lifecycle; final staging test validates reachability. |
| ASM-014 | review | Use the documented Nginx image tag and make the deployment digest configurable until the official digest is confirmed. | The docs require a digest-pinned image but do not include the digest. | A production-like deployment must resolve and freeze the digest before release. | Final Docker verification records the resolved digest or promotes a new decision. |
| ASM-015 | accepted | Keep the repository's required Bun version in `package.json` and container images (DEC-051); local Bun `1.3.14` is the expected toolchain. | Image builds and installs previously OOMed on ~1 GB hosts under pnpm. | Hosts without Bun cannot run the JS toolchain locally. | Typecheck/test results state the actual toolchain; container verification is the authoritative pinned-toolchain gate. |
| ASM-016 | accepted | Treat CoreDNS promotion as a fixed control-helper operation: write the Corefile through Docker's archive API, synchronize zone files through a control-only shared volume, and restart CoreDNS to load changed zone contents. | The official CoreDNS image is minimal and non-root, so in-container `cp`, `rm`, and signal commands are unavailable or unauthorized; a reload-only signal also does not reliably reload changed zone files. | The control helper retains the only Docker socket and CoreDNS has a short controlled restart during apply. | Compose verification exercises managed/forwarded queries plus apply and rollback; replace with a zero-downtime data-plane mechanism if required later. |
| ASM-017 | accepted | Use PostgreSQL as the production web persistence mode and reserve the in-memory adapters for `NODE_ENV=test` or an explicit `PROXYCORE_PERSISTENCE_MODE=memory`. | The web and worker run in separate processes, so in-memory desired state cannot produce a durable apply queue or survive restart. | Existing volatile settings/zones must be entered again; production bootstrap and sessions persist in PostgreSQL. | Restart web/worker after creating a zone and verify the same revision/job/state through the API. |
| ASM-018 | accepted | Keep the existing JSONB resolver fields in `installation_settings` as the canonical settings representation for this integration, while normalized resolver tables remain available for a later migration. | The current API already models pools and forwarding rules as nested values and the schema contains both representations without a consistency contract. | Snapshot reconstruction is deterministic without a schema migration; future normalized writes must explicitly supersede this choice. | Persist settings, render the CoreDNS forward blocks, and update this assumption if normalized resolver management is introduced. |
| ASM-019 | accepted | Use PostgreSQL `LISTEN/NOTIFY` for immediate job wake-up, reconcile the durable queue every 300000 ms by default, use a 120-second claim lease, and coordinate `combined` jobs as one revision apply across CoreDNS and Nginx. | The MVP requires continuous processing but does not specify idle resource usage, event recovery, interval, crash recovery, or multi-service ordering. | A worker crash or missed notification is recovered by startup/reconnect scans and the configurable reconciliation interval; both services must pass health before the revision is marked applied. | Poller/notification tests cover combined jobs and listener behavior; Compose verification checks terminal job state and managed DNS answers. |
| ASM-020 | accepted | Saving a zone or DNS record immediately creates a revision and `combined` apply job in the same transaction; no debounce is used. | The operator chose immediate application over batching consecutive edits. | Multiple quick saves can produce multiple ordered jobs and intermediate data-plane reloads; the API returns the queued apply metadata. | Configuration tests verify one queued job per save; worker serialization and status history remain observable through `/api/status`. |
| ASM-021 | accepted | Use an explicitly configured proxy address first; otherwise detect a non-loopback LAN IPv4 on a native host, or initialize from the authenticated request's literal host address in Compose, then persist it as the installation default. | A container cannot reliably discover the Docker host's LAN address, while returning its `172.x` container address would make proxied DNS unusable for LAN clients. | Accessing the panel through a hostname or `localhost` does not provide a LAN address; the operator can set or override the advertised address in Network settings. | Native startup detection, request-host initialization, persistence, and manual override are covered by configuration/API verification. |
| ASM-022 | accepted | Basic Auth passwords are hashed with Nginx `{SHA}` before encryption at rest; the worker materializes htpasswd files into the revisioned Nginx candidate directory on the shared candidates volume, and Nginx config references those absolute candidate paths. | The MVP needs Basic Auth without adding a host-managed secret volume; advanced Nginx input is handled separately as validated server-level directive text. | Candidate retention must keep the current revision's auth files; rotating a password creates a new secret id and new candidate files. | Unit tests cover hash storage, secret retention on edit, and candidate materialization; Compose verification exercises an authenticated proxied hostname. |
| ASM-023 | accepted | Active certificate PEM is retained in desired snapshots; private keys stay in the encrypted secret store; the worker materializes both into the Nginx candidate `certs/` directory for validate/reload. Compose includes a fixed-IP `demo-upstream` at `172.30.0.10` for local proxy smoke tests. | HTTPS apply previously referenced `/etc/nginx/certs` without installing files, which blocked Compose testing. | Certificate PEMs appear in immutable revisions (public material only); private keys never enter snapshots. | Worker render tests cover cert+auth files; Compose bootstrap runbook exercises `demo-upstream` and self-signed HTTPS. |
| ASM-024 | accepted | Store optional custom Nginx input as normalized server-level directive text on proxy settings. Reject braces and top-level Nginx context directives before revision creation; omit generated directives with matching names so operators can override defaults. | The operator needs controls such as `client_max_body_size` without an ever-growing one-field-per-directive UI. | The textarea cannot define `location`, `server`, `http`, `stream`, or `events` blocks; the worker still runs `nginx -t` before promotion. | Domain and renderer tests cover normalization, block rejection, directive rendering, and default override behavior. |

## Explicit non-assumptions

- No real Cloudflare token, ACME account key, domain, private key, or production
  endpoint is invented.
- No deferred product capability is silently implemented as an MVP requirement.
- No raw user input becomes a shell command or CoreDNS directive. Custom Nginx
  input is explicitly limited to validated server-level directive lines.

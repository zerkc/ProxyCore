# enrollment-import-secret-diagnostics

## Objective
Find and fix why enrollment confirm fails at `step=convert` with
`importer: enqueue apply job: materialize imported configuration: import <redacted> is incomplete`,
and make that failure diagnosable and covered by an end-to-end test that models real installs.

## Problem
- v0.6.7 log shows every confirm stage OK until `convert`; `Import` fails at enqueue/materialize.
- Original message is almost certainly `import secrets: secret is incomplete`
  (`apps/api/internal/configuration/sqlite_import_secrets_owners.go:51`: secret `ID == uuid.Nil` or empty `Purpose`).
  `SanitizedMessage` redacted `secrets: secret` as a key/value pair, hiding it (our bug).
- All primary-side `secrets` writers use a non-empty purpose, so the source of the incomplete secret is unknown.
- Existing import tests use ONE fixture with ONE master key and hand-built envelopes; they never model two
  installs. Real deployments always come from the install script: each instance generates its own keys
  (master key, cluster/CA material); nothing autogenerated is shared between primary and node.

## Constraints
- Two instances MUST use independent, install-generated keys in every new test (no shared master/KEK seeds).
- Logs never contain secret values, hashes, IDs of secrets, tokens, URLs. Indexes/counts and constant reasons only.
- English artifacts; conventional commits; no attribution trailers; version bump only in a release PR.

## Tasks
- [x] T1 Split the `import secrets: secret is incomplete` error into distinct sentinels
      (id nil vs purpose empty) carrying the secret index and no values; register in `KnownCauseSentinels`.
- [x] T2 Fix `SanitizedMessage` so ordinary prose like `secrets: secret` is not redacted
      (only real `key=value`/`key: value` with a value that looks like a credential); add regression tests.
- [x] T3 End-to-end test with two independent installs: primary with its own master + generated cluster key
      exports an envelope (real `Export`, real secrets incl. node-credential, certificate key, basic-auth hash,
      Cloudflare token); node with a DIFFERENT master + its own generated keys enrolls and imports; assert secrets
      round-trip re-wrapped with the node master, digest verified, no incomplete secret. Include a case where the
      primary has a legacy secret row with empty purpose and assert the new diagnostic names the reason.
- [ ] T4 Decide fix for the real root cause once T3 reproduces it (record here before changing behavior).

- Verified finding for T4: `snapshot/validate.go:100` checks `secret.ID.String() == ""` (and `:129` the same for
  `owner.UserID`), which is never true for `uuid.UUID` (nil prints `00000000-...`). A secret with a nil id therefore
  passes `validate` and only fails later at import (`import secrets: secret is incomplete`), matching the v0.6.7 log
  (`step=validate ok`, then `convert` fails). An empty purpose WOULD be flagged by the validator, so the broken secret
  most likely has a nil id (inference). Why the primary exports a nil-id secret is still unknown
  (candidate to check: the reserved nil-UUID backup master-key marker row, `backupcore/dbexport/exporter.go:13`).
- T4 proposal (needs user approval, behavior change): compare against `uuid.Nil` in the validator so the failure
